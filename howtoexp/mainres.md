## HunyMOR 危险头扩展的运行时间结论

运行时间来自各实验目录的 `timing_prompt{0,7,18}.csv`。此前直接读取的
`timing.csv` 是最后运行的 prompt 18，只能代表 prompt 18，不能代表三个
视频的总体趋势。

| Prompt | n5 | n100 | n300 | n600 |
|---:|---:|---:|---:|---:|
| 0 | 189.680 s | 191.704 s (+1.07%) | 192.660 s (+1.57%) | 195.937 s (+3.30%) |
| 7 | 189.918 s | 288.969 s (+52.15%) | 241.296 s (+27.05%) | 195.776 s (+3.08%) |
| 18 | 216.171 s | 212.218 s (-1.83%) | 199.282 s (-7.81%) | 195.664 s (-9.49%) |

### 原因分析

- 危险头数量改变的是 Core/Residual 的路由结构，而不是简单按比例增加同一个 kernel 的工作量。风险头会进入 Residual micro 路径；例如 prompt 7 的平均 Residual 行数从 n5 的 `0.096` 增加到 n600 的 `10.994`，非空 Residual 行比例从 `0.00347` 增加到 `0.41652`。
- 总密度是 Core 与 Residual 的联合支持，不能反映两条路径的工作分配、CSR 行长度、bucket 分布和 kernel 形状。因此密度增加与运行时间不是单调关系。
- prompt 7 的 n100/n300 出现了明显的 route/plan 开销：`flashinfer_core_run` 分别为 `26.642/22.577 s`，而 n5/n600 约为 `18.030/18.089 s`；n300 的 `flashinfer_residual_compact` 也达到 `3.546 s`。这导致 prompt 7 的中间配置明显变慢。
- 每个配置只有一次运行，GPU 时钟、缓存、内存分配和调度状态也会造成波动。`e2e_generation_wall` 与 `e2e_generation_gpu` 几乎一致，因此差异不是模型加载或视频编码造成的，但仍应通过多次重复运行确认。
- 详细 timing phase 存在嵌套，不能直接把所有 phase 相加；例如 `flashinfer_core_run` 包含 CSR expand，`flashinfer_residual_micro_run` 包含 residual bucket 执行。

因此，危险头扩展的运行时间是 **prompt 依赖、非单调** 的：prompt 0 随 n 增加略变慢，prompt 7 出现明显中间配置抖动，prompt 18 则表现为 n600 更快。prompt 18 的加速不能推广为“危险头越多越快”。
